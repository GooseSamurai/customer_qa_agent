# T002 Conversation 与 Message：业务和设计学习笔记

## 1. 这份文档的范围

T002 只解决一个问题：

```text
企业标准化客服会话进入系统时，应该长什么样？
```

本任务关注：

- 一次客服接待如何表示；
- 其中每条发言如何表示；
- 两者之间是什么关系；
- 为什么要做这些检查；
- 如果业务场景变化，应该先判断什么，再决定是否扩展结构。

本任务不实现质检模型、订单查询、业务知识检索或人工复核。后面的场景问题用于训练设计思维，不代表要立即写代码。

## 2. 业务对象

### 2.1 Conversation 是一次完整接待

例如：

```text
客户：耳机坏了，买了十几天，可以退吗？
客服：超过 7 天都不能退。
客户：但是商品页面没有说明。
客服：这个我也没办法。
```

这四次发言属于同一次客服接待，因此属于同一个 `Conversation`。

Conversation 保存整次接待共用的信息：

- 这次接待是谁发起的；
- 由哪个客服处理；
- 来自哪个渠道；
- 关联哪些订单；
- 什么时候开始；
- 中间有哪些具体发言。

它可以理解成系统中的一张“质检案件主记录”。

### 2.2 Message 是一条具体发言

一次发言对应一个 `Message`。

上面的例子包含四条 Message：

```text
Message 1：客户询问是否能退货
Message 2：客服回答超过 7 天不能退
Message 3：客户指出页面没有说明
Message 4：客服表示没有办法
```

Message 保存：

- 这条发言的编号；
- 是客户还是客服说的；
- 什么时间说的；
- 具体说了什么。

### 2.3 两者关系

```text
Conversation 1
    └── Message 1..N
```

Conversation 是整体，Message 是组成部分。

Conversation 离开 Message，就没有可质检的内容。Message 离开 Conversation，就缺少这次接待的渠道、客户、客服和订单背景。

## 3. 当前数据结构

### 3.1 Message 的字段

```python
class Message(BaseModel):
    message_id: str
    role: Literal["customer", "agent"]
    timestamp: datetime
    text: str
```

| 字段 | 业务含义 | 为什么需要 |
|---|---|---|
| `message_id` | 单条消息编号 | 以后可以准确找到具体哪句话 |
| `role` | 客户还是客服 | 判断谁说了什么 |
| `timestamp` | 发言时间 | 还原发言顺序和时间范围 |
| `text` | 消息原文 | 模型分析和原话引用需要内容 |

当前只允许：

```text
customer：客户
agent：客服
```

这是因为当前企业标准输入只定义了这两种角色。官方客服、机器人或系统消息没有确认前，不提前加入。

### 3.2 Conversation 的字段

```python
class Conversation(BaseModel):
    conversation_id: str
    channel: str
    customer_id: str
    agent_id: str
    order_ids: list[str]
    start_time: datetime
    messages: list[Message]
```

| 字段 | 业务含义 |
|---|---|
| `conversation_id` | 一次完整接待的编号 |
| `channel` | 会话来自什么渠道 |
| `customer_id` | 客户编号 |
| `agent_id` | 客服编号 |
| `order_ids` | 相关订单编号，可以多个，也可以为空 |
| `start_time` | 接待开始时间 |
| `messages` | 接待中的全部消息 |

### 3.3 `messages: list[Message]` 在做什么

它表达三层意思：

```text
messages 是一个列表
列表里可以有多个元素
每个元素都必须满足 Message 的规则
```

企业传入 JSON 时，通常是：

```python
"messages": [
    {
        "message_id": "msg-001",
        "role": "customer",
        "timestamp": "2026-09-21T10:00:00+08:00",
        "text": "我要退款",
    }
]
```

Pydantic 会做两件事：

1. 检查 messages 是不是列表；
2. 把每个字典转换成 Message 对象。

最终结果类似：

```python
Conversation(
    messages=[
        Message(
            message_id="msg-001",
            role="customer",
            timestamp=datetime(...),
            text="我要退款",
        )
    ]
)
```

如果写成 `list[dict]`，系统只知道这里有一个列表，但不会检查每个字典中是否有角色、时间是否合法、消息编号是否重复。

### 3.4 `Field(min_length=1)` 在做什么

它表示 messages 至少要有一条消息。

合法：

```python
"messages": [message1]
"messages": [message1, message2]
```

非法：

```python
"messages": []
```

原因：

```text
没有消息
→ 没有对话内容
→ 没有质检对象
→ 没有可以引用的原话
```

所以空会话应该在进入模型前被拒绝。

### 3.5 为什么 message_id 不能重复

后续质检结论需要说明：

```text
问题对应哪条消息
消息是谁说的
原话具体是什么
```

例如：

```text
质检问题：客服可能错误解释售后规则
对应消息编号：msg-002
原话片段：超过 7 天都不能退
```

如果同一个会话里有两个 `msg-002`，系统无法确认引用的是哪一条，证据就失去准确性。

## 4. 为什么这样设计

### 4.1 为什么不把对话拼成一大段文字

拼接方案类似：

```text
客户：...
客服：...
客户：...
```

实现简单，但会丢失：

- 每条消息的编号；
- 每条消息的角色；
- 每条消息的时间；
- 每条消息的边界。

后续模型即使理解了内容，系统也无法可靠确认它引用的是哪条具体发言。

### 4.2 为什么使用 Pydantic

Pydantic 负责把外部数据转换成系统内部对象，并检查：

- 必填字段；
- 角色是否允许；
- 时间是否可解析；
- messages 是否是消息列表；
- message_id 是否重复。

这样，错误数据在系统入口就会被发现，而不是流到后面的质检流程。

### 4.3 为什么不用普通字典

普通字典没有稳定约束。

下面两个字典都能被普通代码接受：

```python
{"role": "customer"}
{"role": "customerr"}
```

但第一个缺少内容，第二个角色拼错。

使用 Pydantic 后，两者都会在入口失败，调用方可以明确知道数据格式不正确。

### 4.4 为什么不用普通数据类

普通数据类可以声明字段，但外部传入的通常还是字典。它不会自动完成：

- 字典转对象；
- 时间格式转换；
- 嵌套消息转换；
- 多条消息之间的整体检查。

Pydantic 更适合处理这种外部输入。

## 5. 一次完整业务过程

```text
企业传入 Conversation
        ↓
检查 conversation_id、channel、order_ids、start_time
        ↓
逐条检查 Message
        ↓
确认角色只能是 customer 或 agent
        ↓
确认 messages 至少一条
        ↓
确认 message_id 不重复
        ↓
得到结构化 Conversation 对象
        ↓
后续模型读取消息进行质检
```

质检结论以后需要引用：

```text
message_id：哪一条消息
role：这条消息是谁说的
原话片段：具体引用了哪一段内容
```

三者一起使用，结论才能回溯到原始会话。

## 6. 业务场景设计问题

这些场景当前不实现，但用来训练“业务变化时先判断什么”的能力。

### 6.1 如果出现系统消息怎么办？

系统消息可能是：

```text
订单已创建
会话已转接
退款流程已发起
```

先判断它是不是某个人说的话。

如果它只是流程状态，更适合作为 Conversation 的附加事件，而不是客户或客服发言。

如果它需要进入 messages，则需要确认：

- 是否增加 `system` 角色；
- 模型是否要把它当作对话上下文；
- 质检问题是否可以引用系统消息作为证据；
- 原有测试和规则是否需要调整。

不能只增加一个角色值就结束。

### 6.2 如果官方客服介入怎么办？

可能出现：

```text
普通客服
人工专员
平台官方客服
机器人客服
```

不要把全部身份都塞进 role。

更清晰的方式是区分两个维度：

```text
role：消息属于哪个对话参与方
sender_type：具体是什么类型的发言者
```

例如：

```text
role = agent
sender_type = human_agent
```

或者：

```text
role = agent
sender_type = official_agent
```

这样增加官方客服、机器人或专员时，不必不断改变 role 的含义。

### 6.3 如果图片或视频消息出现怎么办？

当前只有：

```text
text: str
```

图片和视频不能直接写进 text。

未来需要先判断：

- 媒体内容是否参与质检；
- 模型是否能理解图片和视频；
- 只需要保存链接，还是需要提取内容；
- 质检结论如何定位到具体媒体。

可能的设计是增加：

```text
message_type: text / image / video
image_url
video_url
```

但当前业务没有要求，不应提前实现。

### 6.4 如果机器人转人工怎么办？

机器人转人工会产生两类内容：

```text
机器人说过的话
发生转接的事件
```

机器人发言仍然可以是 Message，但需要记录更具体的发言者类型。

“发生转接”更像会话事件，不一定属于客户或客服的一条发言。需要判断放在 Conversation 事件中，还是作为一种特殊消息。

核心原则：

```text
对话内容放 Message
会话状态变化放 Conversation 或独立事件
```

### 6.5 如果同一个会话中有多个客服怎么办？

同一个 Conversation 可能先从机器人开始，再转普通客服，最后转专员。

此时仅靠 `agent_id` 可能不足以说明每条回复属于谁。

需要区分：

- Conversation 当前由谁负责；
- 每条 Message 具体由谁发；
- 发言者是机器人、普通客服还是官方客服。

可以增加消息级发言者信息，或者在 Message 中增加 sender_id。但不能默认整次会话只有一个客服。

### 6.6 如果客户连续发送多条消息怎么办？

每条客户发言都应该是独立 Message。

例如：

```text
客户：订单还没到
客户：已经等了三天了
客户：你们怎么处理？
```

这是三条 Message，而不是一条拼接文本。

这样可以保留每条消息的时间、编号和原文，后续引用也更准确。

### 6.7 如果客服一次回复被拆成多条消息怎么办？

每条客服回复仍然是一条 Message。

如果业务需要把它们视为一组，可以增加“回复组编号”或“关联消息编号”。但是否需要，取决于质检和展示场景。

不能默认把所有连续客服消息合并，因为每条消息都可能是独立证据。

### 6.8 如果消息被撤回或删除怎么办？

要考虑：

- 撤回后原内容是否仍然需要审计；
- 质检是否基于撤回前的内容；
- 是否保存消息状态；
- 是否需要保留历史版本。

不能直接删除原始内容，否则已产生的质检结论可能失去依据。

这类需求需要业务、合规和审计共同确认，不能只改代码。

### 6.9 如果消息时间缺失或顺序混乱怎么办？

Message 中有 timestamp，但时间相同或上游缺少顺序时，单靠时间可能无法确定先后。

需要先确认企业是否提供稳定的消息顺序编号。

如果业务要求严格顺序，应增加消息序号或来源顺序。当前 T002 没有这个字段，是因为企业输入契约暂未要求。

### 6.10 如果出现纯图片、纯视频、没有文字的消息怎么办？

当前 `text` 是必填字符串。纯媒体消息如果没有文字，就不符合当前结构。

未来必须先确认：

- 空文字是否允许；
- 媒体是否作为消息主要内容；
- 媒体内容是否参与质检。

不能为了支持媒体，简单把链接塞进 text。

### 6.11 如果系统发送订单卡片或活动卡片怎么办？

先判断它是消息还是事件。

如果卡片是系统自动推送，可能属于系统消息或会话事件；如果有客服主动发送，也可能属于客服消息。

需要记录：

- 发送者；
- 内容类型；
- 卡片对应的订单或活动；
- 是否需要质检。

### 6.12 如果上游增加了新字段怎么办？

先判断新字段属于：

- Conversation 级信息；
- Message 级信息；
- 会话事件；
- 未来业务对象。

不能看到一个字段就全部塞进 Conversation。每次扩展都要同步检查模型输入、证据规则、测试和项目文档。

## 7. 面试问题与回答

### 问题 1：如果让你设计一次客服会话的数据结构，你会怎么做？

**回答：**

我会先区分整次接待和单条发言。整次接待作为 Conversation，保存渠道、客户、客服、订单和开始时间；每条发言作为 Message，保存发言者、时间、编号和原文。这样既能表达多轮对话，也能为后续质检保留精确的发言定位能力。

### 问题 2：为什么把会话和消息拆成两个对象？

**回答：**

两者保存的信息不同。会话保存整次接待的共同背景，消息保存单条发言。拆开后，一次会话可以包含多条消息，后续质检也能引用具体是哪条客服发言，而不是只能引用整段对话。

### 问题 3：为什么不把整个会话拼成一段文字？

**回答：**

拼接文本简单，但会丢失编号、角色、时间和消息边界。模型可能看懂内容，但系统无法可靠确认它引用的是哪句话。对于强调证据追溯的客服质检，结构化消息更合适。

### 问题 4：为什么要在数据进入模型前做检查？

**回答：**

企业传入的数据属于外部数据。角色错误、空会话或编号重复如果不提前发现，会流到模型和处理流程中，造成错误判断、无意义调用或证据混乱。入口检查可以让错误更早、更明确地暴露。

### 问题 5：为什么消息列表不能为空，消息编号不能重复？

**回答：**

没有消息就没有质检对象；编号重复则无法确定质检问题具体引用了哪条消息。两条规则都直接服务于后续质检验证，所以应该在数据结构阶段保证。

### 问题 6：为什么选择 Pydantic？

**回答：**

普通字典没有字段约束，普通数据类不能自动处理外部字典和嵌套消息。Pydantic 能把外部数据转换成对象，同时检查字段、时间和消息列表，适合作为系统输入边界。

### 问题 7：如果出现系统消息或官方客服，你会怎么处理？

**回答：**

我会先判断它是不是一条对话发言，以及发言者属于什么类型。如果是流程状态，更可能作为会话事件；如果是官方客服发言，应区分普通客服和官方客服的具体身份。不会直接把所有类型都塞进 role，而是先确认业务责任和质检范围。

### 问题 8：如果出现图片或视频消息，你会怎么处理？

**回答：**

我会先确认媒体内容是否参与质检，再决定消息类型和保存方式。图片和视频不应直接塞进文字字段。如果暂时不分析媒体，就先不增加复杂结构；如果必须分析，再增加媒体类型和对应处理流程。

### 问题 9：如果同一个会话出现多个客服，你会怎么设计？

**回答：**

不能假设整次会话只有一个客服。会话可以有当前负责人，但每条消息也应该能记录具体发送者。普通客服、机器人、官方客服属于不同发言者类型，应该和对话参与方角色分开考虑。

### 问题 10：如果消息被撤回、删除或时间顺序混乱，你会怎么处理？

**回答：**

撤回和删除涉及审计，不能直接丢掉原始内容，需要确认是否保留历史版本和消息状态。顺序则取决于上游是否提供稳定顺序编号；如果只靠时间可能无法判断，应先确认数据来源，不能自己猜测。

### 问题 11：怎样避免数据结构因为未来场景不断膨胀？

**回答：**

先判断新需求属于 Conversation、Message 还是会话事件。只在业务明确要求时扩展，并同步修改测试、模型输入和规则。如果是未来可能用到的能力，先记录设计考虑，不提前实现。

### 问题 12：如何判断一个新字段应该放在 Conversation 还是 Message？

**回答：**

如果信息描述整次接待，例如渠道、客户、客服和开始时间，放在 Conversation；如果信息只描述某一条发言，例如角色、时间和原文，放在 Message。会话状态变化和系统事件则要单独判断，不一定属于某条发言。

### 答案速览

1. **Conversation 和 Message 分别代表什么？**  
   Conversation 是一次完整客服接待，Message 是其中的一条具体发言。前者保存会话背景，后者保存单条消息的角色、时间和原文。

2. **为什么一个 Conversation 包含多个 Message？**  
   因为客服沟通天然是多轮的。每条消息单独保存后，才能准确表达谁在什么时间说了什么，也才能为后续质检引用具体证据。

3. **`messages: list[Message]` 比 `messages: list[dict]` 多做了什么？**  
   `list[Message]` 会让 Pydantic 检查列表结构，并把每个字典转换成 Message 对象；`list[dict]` 只说明这里是列表，不会检查每条消息的字段和内容。

4. **为什么空消息列表必须在入口拒绝？**  
   没有消息就没有对话内容、质检对象和可引用证据。入口直接拒绝可以避免无意义处理和后续错误。

5. **为什么消息编号重复会让证据追溯失效？**  
   因为系统无法确定质检结论引用的是哪一条消息。编号重复会导致证据定位不唯一。

6. **系统消息应该直接增加一个角色值，还是先判断它是不是对话内容？**  
   先判断。它如果是流程事件，应作为会话事件保存；如果确实是对话发言，再考虑增加系统角色，并同步检查模型和证据规则。

7. **官方客服和普通客服更适合通过角色区分，还是通过发言者类型区分？**  
   `role` 负责大类，例如 customer/agent；`sender_type` 负责更具体的发送者，例如 human_agent、official_agent、bot。当前代码没有 `role_id` 或消息级发送者类型，`Conversation.agent_id` 也不代表每条消息的具体发送者。

8. **图片和视频为什么不能直接写入 text？**  
   `text` 只能表示文字内容，无法表达媒体类型、文件地址和媒体处理方式。应先判断媒体是否参与质检，再增加消息类型和附件信息。

9. **同一个会话出现多个客服时，为什么需要消息级发送者信息？**  
   因为 `Conversation.agent_id` 只能表示整次会话的客服编号，不能说明每条回复具体由普通客服、官方客服还是机器人发出。

10. **消息撤回、乱序、纯媒体消息分别要追问哪些业务问题？**  
    撤回要确认是否保留历史版本和审计内容；乱序要确认上游是否提供稳定顺序编号；纯媒体消息要确认文字是否允许为空、媒体是否参与质检以及如何定位媒体证据。
## 9. 一句话总结

Conversation 是一次完整客服接待，Message 是其中的一条具体发言；当前结构通过消息编号、角色、时间和原文保存多轮对话与证据追溯能力，同时坚持只实现当前确认的需求，业务出现新场景时先判断信息属于会话、消息还是事件，再决定如何扩展。
