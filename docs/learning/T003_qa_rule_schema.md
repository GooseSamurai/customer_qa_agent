# T003 QARule：业务和设计学习笔记

## 1. 这份文档讲什么

T003 只解决一个问题：

```text
企业提供的一条质检规则进入系统时，应该包含哪些信息？
```

它不负责：

- 规则怎么存进数据库；
- 规则怎么拼成 Prompt；
- 客服问题怎么判断；
- 是否需要调用订单查询或业务知识检索；
- 后续质检结论怎么生成。

这些内容属于后面的任务。

## 2. QARule 在业务中是什么

企业运营或质检团队会维护一批质检规则，例如：

```text
禁止推诿客户
售后规则解释必须准确
不能承诺没有依据的到账时间
投诉升级必须按流程处理
```

每条规则对应一个 `QARule`。

Conversation 是“被检查的客服会话”，QARule 是“检查时使用的规则”。两者承担不同职责：

```text
Conversation：客户和客服实际说了什么
QARule：企业要求客服应该怎么做
```

模型后续会同时读取 Conversation 和启用的 QARule，再去寻找问题。

## 3. 字段解释

```python
class QARule(BaseModel):
    rule_id: str
    name: str
    dimension: str
    description: str
    positive_condition: str
    exclude_condition: str | None = None
    severity: Literal["low", "medium", "high"]
    need_external_fact: bool
    enabled: bool
    version: str
```

### `rule_id`

规则编号。

作用：后续质检结果需要知道“这个问题命中或违反了哪条规则”。

例如：

```text
rule_id = rule-001
```

### `name`

规则名称。

作用：让运营人员快速看懂规则大致在管什么。

例如：

```text
name = 禁止推诿客户
```

### `dimension`

质检维度，也就是问题属于哪一类。

例如：

```text
服务态度
问题解决
业务准确性
流程规范
投诉升级
```

这里使用普通字符串，是因为企业质量维度可能调整。当前不把所有维度写死在代码里。

### `description`

规则的业务说明。

它解释规则的目的和边界，供人阅读。它不是模型 Prompt，也不应该承担动态政策知识。

### `positive_condition`

正面触发条件。

它描述“出现什么情况时，这条规则可能被命中”。

例如：

```text
客服直接将客户问题推给客户自行处理
```

### `exclude_condition`

排除条件。

它描述“虽然命中正面条件，但什么情况下不应判违规”。

例如：

```text
客服已经说明原因，并且提供了可执行的后续处理方式
```

不是每条规则都有排除条件，所以该字段可以为空。

### `severity`

风险严重程度，只允许：

```text
low
medium
high
```

使用限制值的意义是：不同模块对同一风险等级有一致理解。如果允许随便填写字符串，可能会出现“高危”“严重”“很高”等无法统一处理的值。

### `need_external_fact`

表示这条规则是否可能需要外部事实核验。

例如售后资格规则可能需要订单信息和售后政策，因此可以为真。

它只表示“可能需要”，不表示本任务会真的查询订单或业务知识。

### `enabled`

表示规则当前是否启用。

停用不等于删除。停用规则仍然是合法数据，只是后续加载规则时可以选择不使用它。

### `version`

企业规则版本，例如：

```text
v1
v2
2026-09
```

使用字符串而不是整数，是因为版本格式可能不是简单数字。保存版本后，后续可以追溯某次质检当时使用的是哪一版规则。

## 4. 为什么条件不单独再包一层

当前有两个条件：

```text
positive_condition
exclude_condition
```

没有额外写成：

```text
conditions
    positive
    exclude
```

原因很简单：现在只有两个明确字段，再增加一层对象只会让代码更长，增加阅读和取值层级。

以后如果条件结构变得复杂，再讨论是否拆分，而不是现在提前设计。

## 5. 为什么 QARule 只定义数据

`schemas/` 只负责数据结构和校验。

它不应该：

- 查询数据库；
- 判断规则是否应该执行；
- 调用模型；
- 拼接 Prompt；
- 决定是否调用订单工具；
- 生成质检结论。

这样拆分的好处是：规则数据可以被不同模块复用，而不会把数据库或模型逻辑写进数据结构。

## 6. 业务场景问题

### 6.1 规则被停用后，数据还需要保留吗？

需要。停用表示当前不启用，不等于删除。`enabled=False` 仍然是合法规则。后续是否加载启用规则，是规则加载模块的决定，不属于 QARule 本身。

### 6.2 如果规则没有排除条件怎么办？

允许 `exclude_condition=None`。因为不是每条规则都有例外条件，强制填写反而会制造无意义的空字符串。

### 6.3 如果出现新的严重程度怎么办？

先确认企业是否真的需要新等级，再修改允许值。不能先允许任意字符串，否则每个模块都要猜测不同写法。

### 6.4 如果维度不断增加怎么办？

当前使用字符串，避免把所有业务维度写死。规则的作用范围由企业输入决定，而不是由 Schema 维护业务分类表。

### 6.5 如果规则版本变化怎么办？

每一次规则变化都应该有明确的版本值。后续质检结果需要记录当时使用了哪个版本，否则无法解释历史结论。

### 6.6 如果 `need_external_fact=True`，是否立即查询订单？

不是。这个字段只说明规则可能需要外部事实。是否查询、查询什么、由谁查询，属于后续 Agent 路由和工具执行的任务。

### 6.7 如果规则条件非常复杂，能否写代码？

当前 `positive_condition` 和 `exclude_condition` 是自然语言条件。T003 不实现条件执行。后续如果需要确定性规则，再由对应模块评估，不应把业务逻辑塞进 Schema。

## 7. 面试问题与回答

### 问题 1：你会怎样设计一条质检规则的输入结构？

**回答：**

我会先保留规则的标识、名称、质检维度、说明、触发条件、排除条件、严重程度、是否需要外部事实、是否启用和版本。这样既能表达规则本身，也能支持后续追踪和版本审计。

### 问题 2：为什么规则结构要和数据库、Prompt 分开？

**回答：**

规则结构解决的是数据如何表达，数据库解决的是如何保存，Prompt 解决的是模型如何使用。混在一起以后，任何一方变化都会影响其他模块。分开后，规则数据可以在测试、加载、模型输入和审计中复用。

### 问题 3：为什么严重程度要限制取值，而不是使用任意字符串？

**回答：**

严重程度会被多个模块使用，如果允许任意写法，就会出现无法统一比较和展示的值。限制为明确等级后，数据更稳定，错误也更早被发现。

### 问题 4：为什么排除条件可以为空？

**回答：**

不是每条规则都有例外条件。强制填写会导致大量无意义空字符串。允许为空能准确表达“这条规则没有排除条件”。

### 问题 5：为什么条件不封装成一个额外对象？

**回答：**

当前只有正面条件和排除条件两个字段，直接平铺最简单、最易读。只有条件数量或结构明显变复杂时，增加层次才有价值。

### 问题 6：`need_external_fact` 是否代表立即调用外部系统？

**回答：**

不是。它只是说明这条规则可能需要外部事实。真正是否调用、如何路由、调用哪个工具，是后续流程的职责，不能把调用逻辑塞进规则数据。

### 问题 7：规则停用后应该删除吗？

**回答：**

不应该直接删除。停用只表示当前不启用，历史记录仍可能需要审计。是否加载启用规则，应由后续规则加载逻辑处理。

### 问题 8：如果企业增加新维度或新严重程度，你会怎么处理？

**回答：**

先确认新值是否有明确业务含义，再决定是否扩展字段约束。维度当前使用字符串，便于业务扩展；严重程度如果增加新等级，需要同步更新 Schema、测试和下游解释逻辑。

## 8. 学习检查与答案

### 1. QARule 和 Conversation 分别代表什么？

Conversation 是被检查的客服会话；QARule 是检查会话时使用的企业质检规则。

### 2. 为什么 `exclude_condition` 可以为空？

因为不是每条规则都有排除条件，空值可以准确表达“没有例外条件”。

### 3. `enabled` 和删除规则有什么区别？

`enabled=False` 表示规则停用但仍保留数据；删除会丢失规则历史和审计依据。

### 4. 为什么 `severity` 不直接用任意字符串？

限制取值可以保证不同模块对风险等级的理解一致，避免出现无法统一处理的值。

### 5. 为什么 `need_external_fact` 不负责真正查询订单？

它只表达规则是否需要外部事实，真正查询、路由和调用属于后续流程，不能让数据结构承担业务执行。

### 6. 为什么条件不单独建立一个对象？

当前只有两个固定条件，直接作为字段最简单。只有结构真正复杂时才需要拆分，避免为未来猜测增加层次。

### 7. 为什么 version 使用字符串？

规则版本可能不是整数，例如 `v1` 或 `2026-09`。字符串能保留企业真实版本格式。

### 8. QARule 为什么放在 schemas 目录？

因为它只描述规则字段和校验规则，被模型、加载和测试共同使用，不应该依赖数据库、Prompt 或业务流程。

## 9. 一句话总结

QARule 是企业提供给质检系统的规则数据，只负责把规则的标识、维度、条件、等级、启用状态和版本表达清楚；它不负责规则执行、模型调用或外部工具调用。
