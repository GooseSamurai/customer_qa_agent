# T005-T007 证据基础：业务和设计学习笔记

## 1. 这组任务在做什么

T005、T006、T007 一起打通了证据基础闭环：

```text
准备代表性案例
→ 检查会话说的是什么
→ 检查被引用的原话是否真实
→ 需要订单事实时查询 Mock 订单
```

它们不实现 Agent 路由、业务知识检索、模型调用或最终质检判断。

## 2. T005：为什么要准备代表案例

T005 提供三个基础案例：

- Case A：客服推诿；
- Case B：售后资格解释；
- Case C：退款到账承诺。

这些案例是企业的标准化输入，不包含“哪条规则违规”的判断逻辑。

数据放在：

```text
tests/fixtures/cases.py
```

为什么用 fixtures：

- 测试可以重复使用同一份输入；
- 不需要每个测试重新拼造会话；
- 业务数据和测试逻辑分开；
- 后续验证器和工具可以直接引用同一批案例。

## 3. T006：会话证据校验

### 3.1 它解决什么问题

模型可能输出：

```text
Finding：客服推诿
message_id：msg-a-002
引用原话：不归我们管
```

程序必须回答三个问题：

1. 这个 `message_id` 是否存在；
2. 这条消息是不是客服说的；
3. 引用的原话是否真的出现在这条消息里。

### 3.2 输入和输出

函数：

```python
verify_conversation_evidence(conversation, evidence)
```

输入：

- `Conversation`：完整会话；
- `ConversationEvidence`：消息编号和引用的原话。

输出：

```python
(True, None)
```

表示通过；如果失败：

```python
(False, "message_id not found")
```

### 3.3 为什么不用模型判断

这些检查都可以由普通 Python 精确完成：

- 字符串是否相等；
- 消息编号是否存在；
- 角色是否是客服；
- 原话是否是原文的一部分。

用模型判断会引入额外成本、随机性和不可解释性。确定性检查优先用程序完成。

### 3.4 为什么客户消息不能作为客服违规原话

Evidence 是证明客服存在问题的依据。客户自己的话不能证明客服违规，所以必须限制为 `agent` 消息。

## 4. T007：订单上下文工具

### 4.1 它解决什么问题

有些 Finding 需要订单事实，例如：

```text
耳机购买十几天后是否可以退货？
```

系统必须先知道：

- 订单是否存在；
- 商品是什么；
- 签收多少天；
- 物流状态；
- 售后或退款状态。

### 4.2 当前接口

```python
get_order_context(order_id, fields=None)
```

输入：

- `order_id`：订单编号；
- `fields`：可选，指定需要哪些字段。

输出：

- 字典形式的订单上下文。

如果订单不存在：

```python
OrderNotFoundError
```

工具不会凭空补一个订单或伪造字段值。

### 4.3 为什么工具不判断是否应该查询

是否查询订单，应由后续流程根据 Finding 的 `required_evidence` 决定。工具只负责“有订单编号时返回事实”，不负责路由和质检结论。

### 4.4 为什么使用 Mock 数据

当前阶段企业接口还未接入，测试需要稳定、可重复的数据。Mock 数据让开发和测试不依赖真实订单系统，同时保留后续替换为真实接口的边界。

## 5. 三者的业务关系

```text
Case A/B/C
    ↓
Conversation
    ↓
Finding 引用 ConversationEvidence
    ↓
verify_conversation_evidence 检查原话
    ↓
如果需要订单事实
    ↓
get_order_context 返回订单上下文
```

T005 提供输入，T006 验证会话证据，T007 提供订单事实。三者不重复实现对方的职责。

## 6. 为什么不提前做更多

当前没有实现：

- Agent 路由；
- 业务知识检索；
- RAG 重排；
- 模型调用；
- 最终复判；
- 数据库保存。

原因是 T005-T007 的验收只要求基础数据和两个确定性能力。提前实现会增加依赖和测试复杂度，不能帮助当前任务验收。

## 7. 常见业务场景与回答

### 7.1 如果引用消息不存在怎么办？

返回失败和 `message_id not found`。不能继续把不存在的证据交给模型或人工。

### 7.2 如果引用了客户消息怎么办？

返回失败和 `evidence message must be from agent`。客服质检的客服违规原话必须来自客服消息。

### 7.3 如果原话只是一部分怎么办？

只要原话片段是客服消息原文的一部分，就通过。因为证据允许引用原文中的关键片段，不要求引用整条消息。

### 7.4 如果订单不存在怎么办？

直接抛出明确错误。不能返回空对象冒充“查到了订单但没有字段”。

### 7.5 如果请求的订单字段不存在怎么办？

当前实现不返回缺失字段，也不伪造默认值。调用方可以根据缺失字段决定后续处理。

### 7.6 如果以后接入真实订单系统怎么办？

保持 `get_order_context(order_id, fields=None)` 的外部输入输出不变，只替换内部数据来源。这样上层代码不需要知道订单系统细节。

### 7.7 如果以后增加物流、退款、优惠字段怎么办？

如果只是新字段，可以先加入 Mock 订单上下文并补充测试。只有出现新的独立业务能力时，才考虑拆分工具。

## 8. 面试问题与回答

### 问题 1：为什么要把测试案例放在 fixtures？

**回答：**

案例是测试输入，和验证逻辑不是一回事。单独保存后可以重复使用，修改样例时只改一处，也能避免在多个测试文件里复制同一段会话。

### 问题 2：为什么证据校验不用大模型？

**回答：**

**消息编号是否存在、角色是否正确、原话是否包含在原文里，都可以由程序精确判断**。用模型会增加成本和不确定性，而不会提高这类确定性检查的可靠性。

### 问题 3：为什么要求证据引用客服消息？

**回答：**

客服质检需要证明客服的行为或说法有问题。客户消息可以作为上下文，但不能作为客服违规原话依据，否则会混淆责任主体。

### 问题 4：为什么工具只返回订单事实，不做判断？

**回答：**

工具负责获取外部事实，流程负责决定是否需要事实、使用哪种事实以及最终如何判断。把判断写进工具会让工具和业务流程耦合。

### 问题 5：订单不存在时为什么抛异常？

**回答：**

因为“订单不存在”和“订单存在但字段为空”是两种不同情况。如果直接返回空对象，上层无法区分，容易产生错误结论。

### 问题 6：为什么要支持按字段查询？

**回答：**

不同 Finding 只关心部分事实，例如签收时间或退款状态。按字段返回可以减少无关数据，也让工具输入输出更清楚。当前不查询时则返回整个订单上下文。

### 问题 7：Mock 数据会不会影响后续真实接入？

**回答：**

不会。Mock 只是当前实现细节，上层依赖的是 `get_order_context` 的稳定接口。后续接入真实系统时替换函数内部实现即可。

### 问题 8：T005-T007 完成后还缺什么才能做完整质检？

**回答：**

还缺业务知识检索、Finding 路由、依据复判、证据完整性校验和最终结果编排。当前完成的是会话说、原话验证和订单事实获取的基础能力。

## 9. 学习检查与答案

### 1. T005 的输入数据放在哪里？

放在 `tests/fixtures/cases.py`，只保存代表案例和 Mock 企业数据，不写业务判断。

### 2. T006 的三项检查是什么？

检查消息编号是否存在、消息是否来自客服、引用原话是否出现在原文中。

### 3. 为什么 T006 不只检查编号？

因为编号存在不代表原话真实存在，也不代表证据来自客服消息。

### 4. T007 的输入和输出是什么？

输入是订单编号和可选字段列表，输出是对应的订单上下文字典；订单不存在时抛出明确异常。

### 5. 为什么订单工具不决定调用时机？

因为调用时机属于后续流程和路由职责，工具只负责执行查询。

### 6. 为什么需要 Mock 订单数据？

让开发和测试在没有企业真实系统的环境下仍能验证接口和错误分支。

### 7. 这三种能力分别在哪一层？

代表案例在测试数据层，会话证据校验在 evidence 层，订单查询在 tools 层。

## 10. 一句话总结

T005 提供可复用的业务案例，T006 用确定性程序检查客服原话，T007 用简单 Mock 工具返回订单事实；三者共同为后续 Finding 路由、复判和证据完整性校验提供基础。
